# 4. Credentials are set on first run, never on the command line

Status: accepted · 2026-09

## Context

fogping took credentials as arguments — `fogping user=admin passwd=secret` — and
when none were given it served an open console in read-only mode, with `--edit`
required to make it writable.

Both idioms assume a person at a terminal. A Windows service has neither.

Worse, a service's command line is stored in the registry under
`HKLM\SYSTEM\CurrentControlSet\Services`, which is readable by every account on the
machine. A password passed to `install` would be a password published locally.

## Decision

Follow what Technitium DNS does. No credential on the command line, no config file,
no read-only mode. The first browser to reach the console gets a setup screen,
creates the admin account, and the window closes permanently. The hash lives in the
`settings` table of the same database as everything else.

Hashing is PBKDF2-HMAC-SHA256 at 600,000 iterations (OWASP's 2023 floor), from the
Go 1.24 standard library.

## Consequences

- There is no unauthenticated state after first run, and no anonymous read path.
  That is stricter than fogping: an open console would expose which hosts this
  machine watches, which is itself a map of the network.
- `--edit` is gone. Authentication replaced it.
- There is a first-run window, between service start and the first browser, during
  which anyone who can reach the port can claim the account. This is the same
  window Technitium leaves open, and it is why `install` prints the console URL and
  tells the operator to open it now. A future version can narrow it by binding
  loopback-only until setup completes.
- bcrypt or argon2 would resist offline cracking better, and both are third-party.
  For a LAN-reachable console the threat is online guessing, not a leaked hash
  database, and a stdlib KDF at a real iteration count is the better trade for a
  zero-dependency binary. The stored format is versioned (`pbkdf2$sha256$<iters>$…`)
  and the iteration count is read back from the record, so this can be raised
  without locking anyone out.
- Changing the password invalidates every session, so a stolen cookie cannot
  outlive the password it was issued against.
